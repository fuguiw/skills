# doc-lint

按文档的目标读者，将其改为结构清楚、简洁、专业、自然的中文。读者和用途按以下顺序确定：用户本次的要求；frontmatter 中的 `audience`、`purpose`、`doc_type`（doc-draft 起草时写入）；文档本身的用途和内容，如面向研发、产品、运维或决策者。

## 修改范围

- 优先处理用户指定的文件或段落；未指定时，沿用当前会话正在编辑的文档。无法确定对象时再询问，不默认改写整个文档目录。
- 用户要求“执行 doc lint”“润色”时，直接修改文件；要求“只检查”“给建议”时，仅报告问题。
- 编辑前读取文件最新内容，保留用户刚加入的信息。按段修改，避免用旧稿覆盖新内容。
- 本任务处理结构、语言和表达。保留技术判断、架构分工、示例、限定条件及引用，不借润色调整方案或扩大范围。

## 结构

先看结构，再改句子。读者能否很快找到结论，主要取决于结构，而不是措辞。

按每节承担的作用检查，不看标题叫什么：

- 开头能单独回答读者最先要知道的事。不同类型的文档，开头要回答的问题不同：

  | doc_type | 开头要回答 |
  |---|---|
  | proposal（方案、决策） | 要做什么决定，推荐哪个方案，代价是什么 |
  | research（调研、对比） | 结论是什么，依据有多可靠，哪些还没核实 |
  | status（现状、计划） | 做到哪一步，下一步做什么，需要谁做什么 |

  其他类型的文档，按读者读完后要做的判断或行动确定开头。
- 每节只承担一个作用；结论、决定和待办没有埋在依据或过程后面。
- 同一内容没有在多节重复；没有不提供信息的“总结”“展望”等章节。
- 标题说明本节内容，层级与内容的从属关系一致。

修改分两档：

1. **章节内部，直接改。** 结论、建议和待办放在所在章节或段落的开头，再给依据。一大段混着“已定、已做、待做”时，按这些状态分组。并列项较多且各带说明时，拆成列表。
2. **跨章节，先提方案。** 补开头摘要、跨章节移动内容、拆分或合并章节、修改标题和编号，都先列出改动清单（改什么、为什么、可能影响哪些引用），用户确认后再改。章节编号、标题和阶段名可能被其他文档引用，跨章节移动也最容易改变原意。用户明确要求调整结构时，可以直接改，并在报告中列出。

## 写作规则

### 简洁、具体

- 直接说明谁做什么、为什么需要、有什么限制。删除不增加信息的开场、过渡和结尾总结。
- 一段集中说明一个问题。拆开嵌套长句，合并重复论点，删除同义反复。
- 优先使用具体动词，如“保存”“读取”“派发”“恢复”“通知”。减少“实现……能力”“承载……价值”“形成……体验”等抽象表述。
- 不为压缩篇幅删掉因果关系、必要示例或技术边界，不设置固定删减比例。
- 真正需要比较时用表格，职责或步骤并列时用列表。不要把所有段落机械改成列表。

### 让读者一遍读懂

作者自用的笔记常写成电报体，作者自己读得懂，其他读者却要反复读。这类表达也要改，即使没有套话。

- 把用分号、顿号串起的长串和缺主语、缺动词的短句，改成有主语、有动作的句子。
- 写明“其”“该”“此”等指代的对象。

### 去除 AI 套话和翻译腔

- 不使用“这不是……，而是……”“真正的……是……”等先否定再强调的修辞。直接写出判断；必要的技术对比仍应保留。
- 删除无实际作用的“值得注意的是”“更重要的是”“从本质上讲”“综上所述”等引导语。
- 避免“赋能”“抓手”“闭环”“底座”等口号化用语，以及“带回结果”“请求决策”“保持工作推进”等英文表达的生硬直译。
- 按中文习惯安排主语、动作和对象，减少名词堆叠、过长定语和无必要的被动句。
- 按上下文判断措辞，不把词表当作机械禁用表。技术上准确的“生命周期”“上下文”“编排”等术语可以保留。

### 保留技术含义

- 保持技术用语、产品名、组件名、API、路径和标识符的原有拼写，如 ReAct、PTC、microVM、Multi-Agent、SSE、SOUL.md。不强行翻译（注意大小写），也不为显得专业新增英文。
- 统一同一概念的叫法；明确区分产品能力、运行机制和部署方式，避免精简后混为一谈。
- 保留“拟”“建议”“已实现”“待验证”等状态，以及“默认”“按需”“授权范围内”等限定。不得将目标方案写成已实现能力，将推断写成事实。
- 拆句、合并或移动内容时，原文承诺的强度不变。情态（建议、应、可、必须）、执行人（由人执行、由系统执行）、范围（所有、实际、当前）和否定条件，都不能随句式变化而升级、降级或收窄。例如把“建议先灰度再全量”移到段首时，仍写“建议”；“由值班人确认”不能简化为“人工确认”；“会覆盖已有配置”不能改成“可能影响配置”。句式改动越大，越容易在这里走样。
- 保留引用及其对应论断。未经核实，不补充竞品架构、性能收益或产品行为等事实。
- 纯语言修改通常无需联网。若某处必须核实事实才能修改，只查必要来源；无法确认时保留原意，并简要指出疑问。

## 改写示例

以下示例用于判断语感，按原文含义调整，不做全局替换。

| 原表述 | 建议表述 |
|---|---|
| 在需要时带回结果或请求决策 | 需要时汇报进展或结果，遇到需要用户决定的事项再询问 |
| 统一承载长任务、个人环境和多任务并发 | 统一管理长任务、个人环境和并发任务 |
| 让可编程执行成为复杂任务的默认路径 | 默认通过代码处理复杂任务 |
| Front Agent 负责最终面向用户的研究表达 | Front Agent 负责向用户解释研究结果 |
| 单个用户的资源消耗需要可计量、可限制 | 需按用户统计并限制资源消耗 |

## 执行与复核

1. 通读全文，确定读者和用途，确认论点、术语和章节关系。
2. 按“结构”一节检查：章节内部的问题直接改，跨章节的问题列入结构建议。
3. 再处理句子：重复、长句、电报体、抽象表达和翻译腔。读者一遍能读懂、且自然准确的表达无需改动。
4. 对照修改前后的差异，检查是否遗漏信息、改变语气强度或技术含义。尤其注意状态、权限、数据来源、并发关系和故障恢复条件，并逐处核对被拆开或移动过的句子中的情态、执行人和范围。
5. 通读修改后的全文，检查衔接、主语和术语是否一致；检查 Markdown 层级、表格、代码围栏、链接及 Mermaid 是否被误改。未修改的代码和图示不必重新运行测试。
6. 读者测试（可选）：用户要求时，或做了跨章节调整之后，按 [references/reader-test.md](references/reader-test.md) 用修改前的原文出题，让没有上下文的读者只读新版作答。文档是刚起草的、且用户提供了材料时，改用材料出题。
7. 按以下各项简要报告，没有内容的项省略：
   - 已改：修改的文件和主要改动；
   - 结构建议（待确认）：跨章节改动清单；
   - 事实疑问：无法确认、按原意保留的地方；
   - 读者测试：结果，以及据此做的修改。

   篇幅变化可作为补充，不作为质量证明，也不声称自动检查能够证明“没有 AI 味”。

该 skill 以语义和语感审阅为主。关键词搜索与格式检查只能辅助发现问题，不能替代逐段阅读。
